# Category Labeling Feature Plan

## Overview
Add category labeling to shopping items with grouping, reordering capabilities, and backwards compatibility for existing uncategorized items.

## Requirements Summary
- Items grouped by grocery store section category
- Ability to reorder categories (e.g., produce first, then meats)
- Category required when creating new items
- Searchable dropdown with option to add new category if no match
- Backwards compatibility: prompt user to categorize existing uncategorized items

---

## Implementation Steps

### Step 1: Database Schema Updates
**Status:** In Progress  
**Description:** Update database models to support categories and category ordering

#### 1.1 Create Category Model/Schema
**Location:** `server/models/Category.js` (or similar)

**Schema Fields:**
- `_id` (ObjectId) - Auto-generated by MongoDB/Mongoose
- `name` (String, required, unique) - Category name (e.g., "Produce", "Meats", "Dairy")
- `userId` (ObjectId, optional, default: null) - For future user support, nullable for now
- `order` (Number, default: 0) - Display order for this category (lower numbers appear first)
- `createdAt` (Date, default: Date.now) - Timestamp
- `updatedAt` (Date, default: Date.now) - Timestamp

**Indexes:**
- Unique index on `name` (or `name + userId` if user-specific uniqueness needed later)
- Index on `order` for efficient sorting

**Validation:**
- Name must be non-empty string
- Name should be trimmed and potentially normalized (e.g., capitalize first letter)

---

#### 1.2 Update Item Model/Schema
**Location:** `server/models/Item.js` (or existing item model file)

**Changes:**
- Add `categoryId` (ObjectId, ref: 'Category', optional/nullable) - Reference to Category model
  - Optional/nullable for backwards compatibility with existing items
  - When category is deleted, this should be set to null (not cascade delete)
- Keep all existing item fields unchanged

**Indexes:**
- Index on `categoryId` for efficient queries when grouping by category

**Validation:**
- If `categoryId` is provided, it must reference a valid Category document
- For new items (after feature launch), `categoryId` will be required (enforced at API level, not schema level for flexibility)

---

#### 1.3 Category Order Storage Mechanism
**Approach:** Store order directly in Category model

**Implementation:**
- `order` field in Category schema (Number type)
- Default order: 0 for all categories
- When categories are reordered, update the `order` field for each affected category
- Categories sorted by `order` ascending, then by `name` as secondary sort

**Alternative Consideration:**
- Could use a separate CategoryOrder collection, but storing in Category model is simpler for single-user app
- If multiple users added later, order would be per-user, so might need separate collection then

**For Now:**
- Store order in Category model
- Design allows for future migration to separate collection if needed

#### 1.4 Database Migration Strategy for Existing Items

**Migration Script:** `server/migrations/addCategoriesToExistingItems.js` (or similar)

**Steps:**
1. **Check for existing items without categoryId:**
   - Query all items where `categoryId` is null or doesn't exist
   - Count uncategorized items

2. **Create default "Uncategorized" category (optional):**
   - Only create if uncategorized items exist
   - Name: "Uncategorized"
   - Order: 9999 (appears last)
   - This allows items to have a category reference while user categorizes them

3. **Migration Options:**
   - **Option A (Recommended):** Leave items with `categoryId: null`
     - Items remain uncategorized
     - User will be prompted to categorize via modal
     - Cleaner approach, no assumptions about category names
   
   - **Option B:** Assign all to "Uncategorized" category
     - Creates default category
     - All items have a category reference
     - User can then recategorize

4. **Migration Execution:**
   - Run migration script once before deploying feature
   - Can be run manually or as part of deployment process
   - Should be idempotent (safe to run multiple times)

**Migration Script Structure:**
```javascript
// Pseudo-code structure
async function migrateExistingItems() {
  const uncategorizedItems = await Item.find({ categoryId: { $exists: false } });
  
  if (uncategorizedItems.length > 0) {
    console.log(`Found ${uncategorizedItems.length} uncategorized items`);
    // Option A: Leave as null (recommended)
    // Option B: Create "Uncategorized" and assign
  }
}
```

#### 1.5 Handle Category Deletion (Orphaned Items)

**Strategy:** When a category is deleted, set all items' `categoryId` to `null`

**Implementation:**
- In category deletion logic (API endpoint):
  1. Find all items with the category being deleted
  2. Set their `categoryId` to `null`
  3. Then delete the category
  4. Items become uncategorized (user can recategorize later)

**Alternative:** Soft delete (mark category as deleted but keep it)
- Not recommended for this use case - simpler to handle null categoryId

#### 3.5 Create New Category Flow

**User Flow:**
1. User types category name that doesn't exist
2. "Create new category: [name]" option appears
3. User clicks option or presses Enter
4. API call to create category
5. New category is selected automatically
6. Component updates with new category in list

**Implementation:**
```javascript
const handleCreateCategory = async (categoryName: string) => {
  setIsCreating(true);
  try {
    const response = await fetch('/api/categories', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ name: categoryName.trim() })
    });
    
    if (!response.ok) {
      throw new Error('Failed to create category');
    }
    
    const newCategory = await response.json();
    
    // Add to local categories list
    setCategories(prev => [...prev, newCategory].sort((a, b) => a.order - b.order));
    
    // Select the new category
    onChange(newCategory._id);
    
    // Call optional callback
    onCategoryCreated?.(newCategory);
    
    // Close dropdown
    setIsOpen(false);
    setSearchQuery('');
  } catch (error) {
    // Handle error (show error message, etc.)
    console.error('Error creating category:', error);
  } finally {
    setIsCreating(false);
  }
};
```

**Error Handling:**
- Handle duplicate category name (show error message)
- Handle network errors
- Handle validation errors from API

## Design Decisions

### Category Storage
- **Separate categories table/collection** with 1-to-many relationship (category → items)
- **Full CRUD capabilities** for categories
- **Handle orphaned items**: When a category is deleted, items should be marked as uncategorized (not deleted)

### User System
- Categories are user-specific, but app doesn't have user system yet
- Design schema to be ready for future user support (e.g., add userId field that can be null for now)

### Backwards Compatibility
- **Optional categorization**: Users can skip and categorize later
- **Categorization modal**: Button to open modal popup to categorize uncategorized items one at a time
- Users are NOT forced to categorize before proceeding

### Category Reordering
- **Shopping list view**: Items grouped in category rectangles with up/down buttons in upper right corner (visible while scrolling)
- **Categories list page** (new page): Up/down arrows AND drag-and-drop functionality
